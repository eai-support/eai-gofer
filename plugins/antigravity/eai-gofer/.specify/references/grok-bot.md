# Gofer In Grok Bot

Grok Bot is a separate cloud-computer product. Local Grok Build access does not
prove Bot access. Do not run CLI update commands against the desktop app.

## Persistent Bot Description

Use the following description for a dedicated Gofer Bot. Keep existing company
rules and approval boundaries. Do not create or edit other Bots automatically.

> Help me research, design, build and validate with EAI Gofer. Use concise
> business language and the Gofer controlled-English rules on every request,
> even without `/eai`. Read the approved workspace's current Gofer skill and
> feature records. Continue the current feature; do not restart its pipeline.
> Confirm non-app work once and skip EAI tenant setup for that work. For app
> delivery, prefer the EAI platform and apply checks for the current build
> stage. Keep unfinished work explicit. Ask before login, installation, paid
> work, external messages, cloud provisioning or production changes. Never treat
> another Bot as a separate security boundary. Do not change models or infer
> account access from a CLI.

## One-Time Setup Request

> Set up Gofer for this Bot only. First identify the Bot's cloud workspace and
> the repository or public Gofer bundle I approve. My computer's local folder is
> not automatically available to you. Ask before cloning private repositories,
> copying files or starting a login. Do not copy my local credentials.
>
> In the approved workspace, locate `.grok/skills/eai/SKILL.md` and all Gofer
> `.specify` scripts and stages. Verify the package version and helper commands
> before use. If they are missing, explain what must be installed and ask first.
> Save an `eai` skill that loads those current workspace instructions, preserves
> the full internal pipeline and follows the persistent Bot description. Keep
> maintenance separate: `eai-update` runs only on an explicit update request. If
> a supported plugin import is available, verify its format in this app before
> using it. Do not assume a CLI plugin is a supported Bot package.
>
> Test one harmless research request. Read a fresh marker from the approved
> workspace and return it with the Gofer version and chosen path. Report any
> missing workspace, login, skill or script as blocked. Do not schedule work,
> connect customer tools, deploy, or claim the app pipeline passed.

Enable the saved skill for this Bot in Settings > Plugins > Yours. Check the
desktop `/` menu. The saved description guides every request; a prompt rule is
not a host-enforced interceptor. Verify both a request with `/eai` and one
without. Do not claim always-on execution from the description alone.

## Acceptance Evidence

- Record the actual desktop version, selected Bot and approved cloud workspace.
- Verify the current skill source and all internal stages in that workspace.
- Test non-app routing and a local MVP without demanding unimplemented auth.
- Verify a changed requirement updates its feature records before further work.
- Verify preview, test and release claims against real evidence, not server
  launch.
- Check permissions independently; separate Bots can share files and sign-ins.
- Test updates through the actual supported app flow. Do not overwrite user
  skills.

Keep raw account details, credentials and private workspace identifiers out of
public reports and shared Bot profiles. Do not create a public Bot share link
without approval. Desktop installation, saved-skill creation and real execution
remain separate checks; no CLI result can satisfy them.
